## 1. 배경 (Why)

현재 육아벨에는 **사용자가 운영자에게 연락할 수단이 전혀 없다.** 설정 화면(`app/settings/page.tsx`) "기타" 섹션에는 개인정보 보호정책 / 서비스 약관 2개만 있고, 5개 레포 어디에도 문의 관련 화면·엔드포인트·모델이 없다.

이것이 문제인 이유:

1. **스토어 심사·법적 요구** — App Store / Google Play 심사와 개인정보처리방침 고지 의무상 사용자가 사업자에게 연락할 수단이 필요하다. 정책 페이지에 이메일만 적어두는 것은 최소 요건일 뿐, 앱 내 접점이 없으면 이탈로 이어진다.
2. **초기 서비스의 피드백 손실** — 지금은 버그·불만·기능 요청이 스토어 리뷰나 이탈로만 드러난다. 앱 내 접수 창구가 없으면 개선 사이클이 늦어진다.
3. **탈퇴 직전 사용자 회수 불가** — 계정 탈퇴는 구현돼 있으나(`docs/features/20260519-settings.md` §3.1), 탈퇴 사유를 듣고 대응할 경로가 없다.

외부 도구(구글폼·채널톡)도 검토했으나 **자체 구현으로 결정** (2026-08-19). 근거는 §7 참조.

## 2. 사용자 시나리오 (What)

- **누가**: 앱 사용자(워킹맘/워킹대디) + 운영자
- **언제**: 설정 화면에서 "문의하기" 진입, 또는 오류·불만 발생 시
- **흐름**:

  **사용자**
  1. 설정 → "기타" 섹션 → **문의하기** 진입
  2. 내 문의 목록 확인 (없으면 빈 상태 + "문의 작성" CTA)
  3. 문의 작성: 유형 선택(선택 사항) → 제목 → 내용 → 답변 받을 이메일(기본값 = 로그인 이메일)
  4. 제출 → 목록에 `접수됨` 상태로 표시
  5. 운영자 답변 시 알림 수신 → 목록에서 `답변 완료` 확인 → 상세에서 답변 열람

  **운영자**
  6. 어드민 → 문의 목록 (상태·유형 필터, 미답변 우선 정렬)
  7. 상세에서 문의 내용 + 작성자 컨텍스트(가입일·온보딩 여부) 확인
  8. 답변 작성 → 저장 시 상태 `답변 완료`로 전환 + 사용자 알림 발송

- **수용 기준**:
  - [ ] 사용자가 앱을 벗어나지 않고 문의를 제출할 수 있다
  - [ ] 제출한 문의와 상태(`접수됨` / `확인 중` / `답변 완료`)를 내 문의 목록에서 볼 수 있다
  - [ ] 운영자가 어드민에서 문의를 조회하고 답변을 저장할 수 있다
  - [ ] 답변 저장 시 사용자에게 알림이 생성된다
  - [ ] 탈퇴한 사용자의 문의도 운영자는 조회할 수 있다 (soft delete 유지)
  - [ ] 문의 본문은 Amplitude로 전송되지 않는다

## 3. 도메인 영향

| 엔티티                   | 변경 종류                         | 비고                                    |
| ------------------------ | --------------------------------- | --------------------------------------- |
| `Inquiry`                | **신규 테이블**                   | User 1:N Inquiry                        |
| `InquiryCategory`        | 신규 enum                         | 선택 입력 (유형 미선택 허용)            |
| `InquiryStatus`          | 신규 enum                         | `received` / `in_progress` / `answered` |
| `User`                   | 관계 추가 (`inquiries Inquiry[]`) | 필드 추가 없음                          |
| `NotificationType`       | enum 값 추가 (`inquiry_answered`) | 답변 알림용                             |
| `NotificationTargetType` | enum 값 추가 (`inquiry`)          | 알림 → 문의 상세 딥링크                 |

> 도메인 의미 문서는 [`../schema/12-inquiry.md`](../schema/12-inquiry.md)에 신규 작성. [`../schema/00-overview.md`](../schema/00-overview.md) 도메인 맵에도 관계 1줄 추가.

### 설계 판단 — 유형(category)을 왜 enum으로 두는가

`docs/features/AGENTS.md` §11은 **자유 텍스트 우선**을 권한다. 문의는 다음 이유로 예외를 둔다.

- 본문(`body`)은 자유 텍스트를 그대로 유지한다 — §11의 취지(정보 손실 방지)는 여기서 충족된다
- `category`는 **운영자 트리아지 전용 보조 필드**이며 **선택 입력(nullable)** 이다. 사용자가 분류하지 않아도 제출된다
- 유형별 문의량은 제품 개선 우선순위 판단에 직접 쓰이는 지표라, 사후 LLM 추출보다 사용자 자기 분류가 신뢰도가 높다

### 설계 판단 — 스레드가 아닌 단일 Q&A

v1은 **문의 1건 = 질문 1개 + 답변 1개**로 고정한다. 재질문은 새 문의로 접수한다.

- 초기 문의량에서 스레드 UI·미읽음 카운트·실시간 갱신의 복잡도는 과투자
- `Inquiry`에 `answerBody`/`answeredAt`을 직접 두면 스키마·쿼리가 단순하다
- 스레드가 필요해지면 `InquiryMessage` 테이블을 추가하고 기존 행을 첫 두 메시지로 마이그레이션하면 된다 (§7 후속)

### 4.1 yougabell-api

#### Prisma schema diff

```prisma
/// 1:1 문의 (docs/features/20260819-inquiry.md).
///
/// v1은 **질문 1 + 답변 1**의 단일 Q&A. 스레드가 필요해지면 InquiryMessage 분리.
/// 사용자가 탈퇴해도 운영 기록으로 남겨야 하므로 User 삭제 시 Cascade가 아닌 SetNull 대신
/// User soft delete(deletedAt)에 의존한다 — User 행 자체는 grace 기간 동안 유지된다.
model Inquiry {
  id       String           @id @default(uuid()) @db.Uuid
  userId   String           @db.Uuid
  category InquiryCategory? // 선택 입력. 운영자 트리아지 보조용
  title    String
  body     String
  /// 답변 받을 이메일. 기본값은 로그인 이메일이지만 사용자가 바꿀 수 있어 별도 보관.
  contactEmail String?
  status   InquiryStatus    @default(received)

  /// 운영자 답변. status가 answered일 때만 채워진다.
  answerBody String?
  answeredAt DateTime?
  /// 답변한 운영자의 Supabase auth user id. User 테이블 FK가 아니다(운영자는 도메인 User가 아닐 수 있음).
  answeredBy String? @db.Uuid

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId, createdAt])
  @@index([status, createdAt])
}

enum InquiryCategory {
  service_error // 오류·장애
  account       // 계정·로그인
  content       // 콘텐츠·미션·로드맵
  suggestion    // 개선 제안
  etc           // 기타
}

enum InquiryStatus {
  received    // 접수됨
  in_progress // 확인 중
  answered    // 답변 완료
}
```

#### 엔드포인트 — 사용자

| 메서드 | 경로             | 요약         |
| ------ | ---------------- | ------------ |
| `POST` | `/inquiries`     | 문의 등록    |
| `GET`  | `/inquiries`     | 내 문의 목록 |
| `GET`  | `/inquiries/:id` | 내 문의 상세 |

공통: `@UseGuards(JwtAuthGuard)` · `@ApiBearerAuth()` · 온보딩 완료 가드는 **skip** (온보딩 중에도 문의할 수 있어야 함 → `@SkipOnboardingCheck()`).

**`POST /inquiries`**

```ts
class CreateInquiryDto {
  category?: InquiryCategory; // 선택
  title: string; // 1~100자
  body: string; // 10~2000자
  contactEmail?: string; // 이메일 형식, 최대 254자
}
```

- 검증: `title` `@Length(1, 100)`, `body` `@Length(10, 2000)`, `contactEmail` `@IsEmail()` + `@MaxLength(254)`
- 처리: `title`/`body` trim 후 저장. `status`는 `received` 고정 (클라이언트가 지정 불가)
- **스팸 가드**: 동일 사용자의 **미답변(`received` | `in_progress`) 문의가 5건 이상이면 거부**. 무제한 등록으로 운영이 마비되는 것을 막는다
- Response `201`: `InquiryResponseDto`

**`GET /inquiries`**

- Query: `page?` (1-based, default 1), `limit?` (1~50, default 20)
- 처리: `userId` 소유분만, `createdAt desc`
- Response `200`: `{ items: InquiryListItemDto[]; total: number; page: number; limit: number }`
  - 목록 항목은 `body`/`answerBody` 전문을 싣지 않는다 (목록 페이로드 절감)

**`GET /inquiries/:id`**

- 처리: 소유자 검증. 타인 문의 조회 시 존재를 노출하지 않기 위해 `404`
- Response `200`: `InquiryResponseDto`

```ts
class InquiryResponseDto {
  id: string;
  category: InquiryCategory | null;
  title: string;
  body: string;
  contactEmail: string | null;
  status: InquiryStatus;
  answerBody: string | null;
  answeredAt: string | null; // ISO
  createdAt: string; // ISO
}
```

#### 엔드포인트 — 운영자

기존 `AdminController` 패턴(`@UseGuards(JwtAuthGuard, AdminRoleGuard)` + `@SkipOnboardingCheck()`)을 따른다.

| 메서드  | 경로                   | 요약                        |
| ------- | ---------------------- | --------------------------- |
| `GET`   | `/admin/inquiries`     | 문의 목록 (필터·페이징)     |
| `GET`   | `/admin/inquiries/:id` | 문의 상세 + 작성자 컨텍스트 |
| `PATCH` | `/admin/inquiries/:id` | 상태 변경 / 답변 저장       |

**`GET /admin/inquiries`**

- Query: `status?` (`received` | `in_progress` | `answered` | `all`, default `all`), `category?`, `q?` (제목·본문 LIKE), `page?`, `limit?` (1~100, default 20)
- 정렬: **미답변 우선** — `status = answered`를 뒤로, 그다음 `createdAt asc` (오래 기다린 문의부터)

**`PATCH /admin/inquiries/:id`**

```ts
class UpdateInquiryDto {
  status?: InquiryStatus;
  answerBody?: string; // 1~4000자
}
```

- `answerBody`가 오면: `status`를 `answered`로 강제 전환, `answeredAt = now()`, `answeredBy = 요청 운영자 id`
- `answerBody` 없이 `status`만 오면 상태만 변경. `answered`로 직접 전환하려는데 `answerBody`가 비어 있으면 `400 ANSWER_BODY_REQUIRED`
- **답변 저장 시 알림 생성** — `Notification`에 `type: inquiry_answered`, `actionType: url`, `targetType: inquiry`, `targetId: inquiry.id`, `targetUrl: /settings/inquiries/{id}` 행 추가. 푸시 발송은 기존 알림 파이프라인이 처리
- 답변을 다시 저장하면 `answerBody`를 덮어쓰되 **알림은 중복 생성하지 않는다** (`answeredAt`이 이미 있으면 skip)

#### 에러 응답

| 코드                      | HTTP | 상황                               |
| ------------------------- | ---- | ---------------------------------- |
| `INQUIRY_NOT_FOUND`       | 404  | 없거나 타인 소유                   |
| `TOO_MANY_OPEN_INQUIRIES` | 409  | 미답변 문의 5건 이상               |
| `ANSWER_BODY_REQUIRED`    | 400  | `answered` 전환인데 답변 본문 없음 |

#### 상태 스키마

**로컬 임시 저장 없음.** 문의는 한 화면에서 완결되는 짧은 입력이고, 온보딩처럼 여러 단계에 걸쳐 작성되지 않는다. 작성 중 이탈 시 내용은 버린다 (§6 저장 전략 참조).

#### middleware / 게이트

`app/settings/**`는 이미 `getAppRedirectPath()` 게이트 아래에 있어 별도 분기 불필요. 단 **온보딩 미완료자도 문의할 수 있어야** 하므로 api 쪽은 `@SkipOnboardingCheck()`를 붙인다 (web에서 온보딩 중 진입 경로는 v1 범위 밖 — §7 참조).

#### 화면 규칙

`DESIGN.md` §4 "헤더·하단 버튼 고정" 규칙 적용 — 작성 화면은 헤더 고정 + 본문 스크롤 + 하단 제출 CTA 고정.

**영향 없음.** 문의 화면은 전부 web(WebView)에서 처리하고, 답변 알림은 기존 `Notification` → 푸시 파이프라인을 그대로 탄다. 알림 탭 시 딥링크(`/settings/inquiries/{id}`)는 기존 `targetUrl` 처리 로직이 담당한다.

- **디자인 토큰 변경: 없음.** 상태 뱃지는 기존 semantic 색상에 매핑
  - `received` → `info.50` 배경 / `info.700` 텍스트
  - `in_progress` → `warning.50` 배경 / `warning.800` 텍스트
  - `answered` → `success.50` 배경 / `success.500` 텍스트

> 디자인 확정 시 본 섹션을 Figma 노드 ID로 교체하고 화면을 재정렬한다.

## 6. 비기능 요구

### 저장 전략

| 축                    | 결정                                                               |
| --------------------- | ------------------------------------------------------------------ |
| 디바이스 로컬 vs 서버 | **서버 DB 단독.** 문의는 운영자가 봐야 하므로 로컬 초안 불필요     |
| 단계별 vs 일괄        | **일괄 atomic POST.** 한 화면 입력 → 1회 제출                      |
| 영속성 등급           | 영구 보존. 사용자 탈퇴 시에도 `User` soft delete 기간 동안 유지    |
| 멀티 디바이스         | 지원 (서버 저장이므로 자동)                                        |
| 작성 중 이탈          | **내용 폐기.** localStorage 초안 저장 안 함 — 짧은 입력이라 과투자 |

### 성능

- 목록 조회 200ms 이하 (`@@index([userId, createdAt])`, `@@index([status, createdAt])`로 커버)
- 목록 응답에 `body`/`answerBody` 전문 미포함

### 보안·개인정보

- 사용자 엔드포인트는 **소유자 검증 필수**. 타인 문의 접근 시 `403`이 아닌 `404` (존재 여부 비노출)
- 운영자 엔드포인트는 `AdminRoleGuard`(Supabase `app_metadata.role === 'admin'`) 통과 필수
- 문의 본문에 개인정보가 포함될 수 있음을 **작성 화면에 안내 문구로 고지**
- 어드민 목록에서 작성자 이름·이메일은 마스킹

### 접근성

- 폼 입력에 `<label>` 연결, 에러는 `aria-live="polite"`
- 상태 뱃지는 색상만으로 구분하지 않고 텍스트 병기

### 분석 이벤트

`lib/analytics.ts` 헤더 규칙 준수 — **개인정보·자녀 식별자·본문 원문을 속성에 넣지 않는다.**

| 이벤트 키             | 발화 시점         | 속성                |
| --------------------- | ----------------- | ------------------- |
| `inquiry_list_view`   | 내 문의 목록 진입 | —                   |
| `inquiry_form_view`   | 작성 화면 진입    | —                   |
| `inquiry_submit`      | 제출 성공         | `category` (enum만) |
| `inquiry_detail_view` | 상세 진입         | `status` (enum만)   |

> `title`·`body`·`contactEmail`은 **절대 이벤트 속성에 포함하지 않는다.** `lib/analytics.test.ts`에 회귀 테스트 추가.
