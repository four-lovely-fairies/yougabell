## 1. 배경 (Why)

현재 육아벨은 **한국어 단일 언어**로 KR 앱스토어에 출시되어 있다 (mobile `v1.1.4`).
미국 앱스토어에서 쓰고 싶다는 요구가 나왔고, i18n 적용 범위를 정하려면 먼저 **"어디까지가 번역이고 어디부터가 현지화인가"**를 나눠야 한다.

이 제품은 UI 문자열보다 **콘텐츠(미션 480건·마일스톤·지식베이스)와 AI 생성물이 압도적으로 큰 비중**을 차지한다. 따라서 `next-intl`을 붙이는 통상적인 i18n 작업만으로는 미국 사용자가 쓸 수 있는 앱이 되지 않는다. 본 문서는 그 격차를 레벨로 쪼개 공수를 매긴다.

### 이 제품 고유의 난점

| 난점                | 내용                                                                                                             |
| ------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 콘텐츠 비중         | UI 문자열 대비 DB 콘텐츠 한글 분량이 **약 10배** (§3 인벤토리)                                                   |
| 근거 출처의 국적    | `MissionSource` / `MilestoneSource`의 citation에 `보건복지부`·`국민건강보험`·`아이사랑` — 미국 사용자에게 무의미 |
| AI 응답 언어        | 시스템 프롬프트가 "한국의 워킹맘·워킹대디" 전제로 하드코딩 + "한국어로 답하세요" 지시                            |
| 건강 정보 심사 요건 | 프롬프트에 이미 App Store 1.4.1 대응이 들어가 있음 — 영어에도 **미국 기관 기준으로** 동일 대응 필요              |
| 아동 개인정보       | 아이 이름·생년월일·특이사항을 수집 → 미국은 COPPA 적용 검토 필요 (한국 기준으로는 커버 안 됨)                    |
| 저장 시점 언어 고정 | `Notification.title/body`, `WeeklyReport*` 는 **생성 시점에 렌더된 문자열**을 저장 → 사후 언어 전환 불가         |

## 2. 사용자 시나리오 (What)

- **누가**: 미국 거주 한인 부모 / 영어권 워킹맘·워킹대디
- **언제**: US 앱스토어에서 앱 설치 → 최초 실행
- **흐름**:
  1. 앱 실행 → 디바이스 로케일(`en-US`) 감지 → 영어 온보딩
  2. 부모·아이 정보 입력 (영어 UI, 영어 플레이스홀더, 미국식 날짜 포맷)
  3. 홈에서 **영어로 된 오늘의 미션** 추천 받음
  4. 미션 수행 → 영어 피드백 화면 → 영어 푸시 알림
  5. 챗봇에 영어로 질문 → **영어로, 미국 기관(CDC·AAP) 근거로** 답변
  6. 주간 리포트를 영어로 수령
- **수용 기준 (레벨별)**: §3의 L1~L3 정의 참조. 최소 합격선은 **L2** — "앱을 켜서 끝까지 쓰는 동안 한글이 한 글자도 안 보인다".

### 4.0 i18n 아키텍처 원칙 — "데이터는 확장, 경로·심사는 단순"

> 2026-08-13 사용자 방향 확정: **번역 확장성은 확보하되, URL 경로와 앱 심사는 단순하게.**
> 아래 3층을 분리하면 둘이 상충하지 않는다.

| 층            | 방침                                              | 근거                                       |
| ------------- | ------------------------------------------------- | ------------------------------------------ |
| 콘텐츠 (DB)   | **N개 언어 확장** — `locale` = BCP 47 **문자열**  | 언어 추가 = `INSERT`만. 스키마 변경·배포 0 |
| 전달 (URL)    | **경로에 locale 없음** — 쿠키 + `Accept-Language` | 딥링크·auth callback·middleware 무영향     |
| 배포 (스토어) | **단일 바이너리 + 단일 앱**                       | 심사 1회. 언어 추가해도 앱 신규 등록 없음  |

#### 원칙 1. locale은 enum이 아니라 문자열

`locale`을 Prisma enum으로 만들면 **언어 추가마다 스키마 변경 + `db push` + 재배포**가 따라온다. BCP 47 문자열 컬럼으로 두면 언어 추가가 데이터 작업으로 끝난다.

#### 원칙 2. 원본(ko)도 번역 테이블에 넣는다

본체 컬럼을 ko로 남겨두면 "ko는 본체 컬럼, en은 번역 테이블"이라는 **이중 조회 경로**가 생겨 조회 코드가 영구히 두 갈래로 갈린다.

- ko 행도 번역 테이블에 적재 → 조회 코드는 `locale` 하나만 본다
- 본체 컬럼(`Mission.title` 등)은 **deprecated 상태로 유지**했다가, 전 클라이언트가 번역 경로로 넘어간 뒤 제거
- fallback 체인은 함수 하나로 통일: `resolveLocale(requested, available)` → `en-GB → en → ko`

#### 원칙 3. URL 경로에 locale을 넣지 않는다

`/en/...` prefix의 유일한 장점은 **SEO와 공유 링크**인데, 이 웹은 **Expo WebView 안에서만 렌더**되므로 둘 다 해당 없다. 반면 비용(mobile 딥링크 · `mobile-entry` · auth callback · `middleware.ts` 전수 수정)은 실재한다.

```
mobile: expo-localization 로 기기 로케일 감지
  → WebView 최초 진입 1회만 ?lang=en
  → web: 쿠키 NEXT_LOCALE 로 승격 후 즉시 리다이렉트해서 쿼리 제거
  → 이후 모든 URL 은 지금 그대로 (/onboarding, /mission, ...)
  → 로그인 후에는 User.locale 이 진실. 쿠키와 다르면 쿠키 갱신
  → API 호출은 Accept-Language 헤더만. 엔드포인트 경로·시그니처 불변
```

- `next-intl`의 **"without i18n routing"** 구성이 정확히 이 형태 (`app/[locale]/` 디렉토리를 만들지 않는다)
- 트레이드오프: 쿠키를 읽는 페이지는 dynamic 렌더가 된다. 이 앱은 이미 인증 기반 동적 페이지가 대부분이라 실손실 미미. 정적으로 두고 싶은 페이지(`/policy/*`)만 예외 처리
- **엔드포인트 시그니처가 안 바뀌므로 OpenAPI 스펙·클라이언트 codegen 산출물 변화가 최소**

#### 원칙 4. 응답에 실제 언어를 실어 보낸다

콘텐츠 응답에 `contentLocale` 필드를 포함해 **fallback이 발생했는지**를 클라이언트·운영자가 감지할 수 있게 한다. 번역 누락을 배포 후에 발견하는 상황을 막는다.

#### 원칙 5. 심사는 단일 앱 + 로컬라이제이션 "추가"로만

- 별도 US 앱 등록 ❌ → 단일 바이너리, App Store Connect에서 en-US 로컬라이제이션 추가 → **심사 1회**
- 언어를 더 붙일 때도 앱 신규 등록 없음 (메타 로컬라이제이션 추가만)
- App Privacy 라벨은 언어 무관 1회 작성
- 심사 노트에 en 데모 계정 + "앱 언어는 기기 설정을 따름" 명시

### 4.1 yougabell-api

**Prisma schema diff (D2 채택 시)**

```prisma
model User {
  // ...
  locale String @default("ko") // BCP 47 문자열. enum 금지 (§4.0 원칙 1)
}

model MissionTranslation {
  missionId     String @db.Uuid
  locale        String // BCP 47. ko 행도 함께 적재 (§4.0 원칙 2)
  title         String
  shortTitle    String
  description   String
  effect        String
  goal          String?
  subThemeLabel String?
  status        String @default("published") // draft | reviewed | published — 감수 워크플로 대비

  mission Mission @relation(fields: [missionId], references: [id], onDelete: Cascade)

  @@id([missionId, locale])
  @@index([locale])
}

// MilestoneTranslation / GrowthStageTranslation / MilestoneCategoryTranslation 동형
// 기존 본체 컬럼(Mission.title 등)은 deprecated 유지 → 전 클라이언트 전환 후 제거
```

**번역 저장 3안 비교** (§7에서 결정)

| 안                                                         | 장점                                 | 단점                                         |
| ---------------------------------------------------------- | ------------------------------------ | -------------------------------------------- |
| **A. 엔티티별 번역 테이블** (위 diff)                      | 타입 안전, Prisma include 자연스러움 | 테이블 4~5개 추가, 필드 추가 시 두 곳 수정   |
| B. 단일 폴리모픽 `ContentTranslation(type,id,field,value)` | 테이블 1개, 필드 자유                | 타입 안전 X, 조회마다 pivot, 인덱스 비대     |
| C. 기존 컬럼을 `Json`으로 (`{ko: "...", en: "..."}`)       | 스키마 변경 최소                     | 기존 데이터 전량 마이그레이션, 부분 인덱스 X |

> **권장: A.** 엔티티가 4~5개로 적고, `db push` 운영(→ [`project_api_db_push_not_migrate`])이라 테이블 추가 비용이 낮다.

**locale 협상 순서**: `User.locale` (로그인 시) → `Accept-Language` 헤더 → `ko` 기본값

**영향 엔드포인트**: 콘텐츠를 반환하는 전 엔드포인트 (`/missions`, `/roadmap`, `/home`, `/weekly-reports`, `/chat`) — **경로·시그니처는 불변**, `Accept-Language` 헤더만 추가로 읽는다. fallback 규칙은 `resolveLocale()` 한 함수로 통일(`en-GB → en → ko`), 응답에 `contentLocale` 포함(§4.0 원칙 4).

**AI 프롬프트** — `ai/prompts/` 3파일을 `ko.ts` / `en.ts`로 분기. 단순 번역이 아니라 **미국 기준 재작성**:

- "한국의 워킹맘·워킹대디" → 미국 맥락 서술
- 건강 안내 fallback 기관: `대한소아과학회·질병관리청(KDCA)·보건복지부` → **`AAP`·`CDC`·`HealthyChildren.org`**
- 존댓말 톤 지시 → 영어에는 무의미 → warm/non-judgmental 톤 지시로 대체

**지식베이스**: `KnowledgeDocument.language` 필드가 **이미 존재** → 스키마 변경 없이 en 문서 병행 적재 가능. 검색 시 locale 필터만 추가.

- CDC 문서 4건: 한국어 번역본을 쓰고 있으므로 **영어 원문으로 교체** (오히려 품질 상승, 공수 낮음)
- 보건복지부 아이사랑 2건: 미국 부적합 → **AAP/Zero to Three 문서로 대체 수집**
- 임베딩 재생성 필요 (Gemini text-embedding-004, 768d)

**알림 언어**: `Notification.title/body`가 렌더된 문자열이므로 **발송 시점에 `User.locale` 조회 → 해당 언어로 생성**한다. 저장 후 언어를 바꿔도 과거 알림은 옛 언어로 남지만 수용 가능. (템플릿 키 + 파라미터 구조로 바꾸는 대안은 공수 대비 이득 없음.)

### 4.2 yougabell-web

- **라우팅**: `next-intl` **without i18n routing** (§4.0 원칙 3). `app/[locale]/` 디렉토리를 만들지 않으므로 **기존 라우트 경로 전부 불변** → mobile 딥링크·`mobile-entry`·auth callback·`middleware.ts` 수정 0.
  - `i18n/request.ts`에서 쿠키 `NEXT_LOCALE` → `Accept-Language` → `ko` 순으로 해석
  - 최초 진입 `?lang=` 쿼리를 쿠키로 승격 후 리다이렉트로 쿼리 제거
  - 로그인 후 `User.locale`과 쿠키 불일치 시 쿠키 갱신
- **문자열 추출**: ~520 라인 → `messages/{locale}.json`. 네임스페이스는 화면 단위(`onboarding.*`, `mission.*`). **키는 영어 slug**(`mission.timer.pauseButton`) — 한국어 원문을 키로 쓰면 카피 수정 때마다 전 언어 키가 깨진다. 언어 추가 = 파일 1개 추가.
  - `lib/*-data.ts`의 fallback 더미 데이터(roadmap/home/mission)도 포함
- **레이아웃**: 영어는 한국어 대비 텍스트 폭이 보통 **1.2~1.4배**. 375px 기준 버튼·칩·카드 타이틀 줄바꿈 깨짐이 다수 예상 → 27개 라우트 전수 확인.
- **포맷터**: `Intl.DateTimeFormat` / `Intl.NumberFormat`. 월령 표기 `"36개월"` → `"3 yr 0 mo"`, `"4개월 차"` → `"Month 4"`. 주간 리포트 요일(`Weekday` enum) 라벨.

### 4.3 yougabell-mobile

- `expo-localization`으로 디바이스 로케일 감지 → WebView URL/`postMessage`로 web에 전달
- `app.json`: `ios.infoPlist.CFBundleLocalizations`에 `en` 추가, 앱 표시명 결정
- 네이티브 에러 문자열 54라인 (Apple/Google 로그인) 영어화
- **App Store Connect**: en-US 로컬라이제이션 추가 — 이름/부제/설명/키워드/**스크린샷 전량 영문 재촬영**
- 앱 이름: 현재 expo `name: "yougabell"`. **영문 브랜드명 확정 필요** (§7)

### 4.4 yougabell-admin

운영자는 한국 팀 → **UI 번역 대상에서 제외**가 기본. 단 D2 채택 시 **번역 검수·수정 화면**은 필요할 수 있음 (선택 항목, §5 공수표).

### 4.5 데이터 최소화 — "이름 → 별칭", "생년월일 → 생년월"

> 2026-08-13 사용자 제안. **채택 시 개발·법무 공수가 모두 줄고, 출시 블로킹 리스크가 크게 낮아진다. 채택 권장.**

#### 무엇을 바꾸는가

| 항목      | 현재                             | 변경                                   |
| --------- | -------------------------------- | -------------------------------------- |
| 아이 식별 | 아이 **이름** (`Child.name`)     | 아이 **별칭 / Nickname** (라벨·카피만) |
| 아이 생일 | 생년월**일** (`Child.birthDate`) | 생년**월**까지만 필수 (일은 `01` 고정) |

#### 개발 공수: 약 **−1 MD (순감소)**

| 작업                                                                                           |         MD |
| ---------------------------------------------------------------------------------------------- | ---------: |
| 별칭 카피·라벨·플레이스홀더 변경 (`child-card.tsx` 외)                                         |       +0.5 |
| `DateBottomSheet`에 `precision="year-month"` 추가 — 일 컬럼 숨김, `daysInMonth` 윤년 검증 제거 | **−1~1.5** |
| **순효과**                                                                                     |  **약 −1** |

**스키마 변경 없음**이 핵심이다.

- `Child.name`은 **필드명 그대로 두고 의미·라벨만 재정의**한다. `nickname`으로 rename하면 api → OpenAPI → web/admin/mobile codegen 연쇄가 발생 → **rename하지 않는 편이 이득**
- `Child.birthDate DateTime @db.Date` 유지, 일을 `01`로 저장 → 월령 계산 호출부 **4곳 전부 무변경**
  (`home/home.service.ts:62` · `missions/missions.service/service.ts:97` · `weekly-reports/weekly-reports.service/service.ts:275` · `ai/context-builder.service.ts:115`)

#### 법무·심사: **−1 MD + 리스크 대폭 하락 (진짜 이득)**

- 육아벨은 **부모가 사용자**이고 아이는 정보 대상이므로 원래도 COPPA의 "directed to children"에 곧바로 걸리지는 않는다. 다만 **실명 + 정확한 생년월일 조합**은 아동 식별자로 보수적 해석 여지가 있어 자문이 길어질 지점이었다
- 별칭 + 생년월이면 식별성이 크게 떨어져 **자문 범위가 좁아지고 App Privacy 라벨에서 "Name" 신고 항목이 빠진다**
- GDPR/CCPA의 **데이터 최소화 원칙**에도 부합 → 향후 EU 확장 시 재작업 없음
- 절감의 본질은 MD가 아니라 **"법무 답변이 늦어지면 출시가 멈추는" 종류의 리스크 제거**

#### 대가와 한계

- **월령 정밀도가 최대 ±30일 흔들린다.** 미션 추천(`recommendedAgeMonthsMin/Max`)과 로드맵이 **월령 구간 단위**라 경계에서만 1개월 어긋난다 → 실사용 영향 미미. 정밀도가 중요한 기능이 생기면 "일(선택 입력)"을 다시 열면 된다
- **별칭이라도 사용자가 실명을 입력하는 것은 막을 수 없다.** 입력 검증은 불가 → 헬퍼 텍스트("실명 대신 애칭을 권장") + 개인정보처리방침 명시로 마무리
- **KR 기존 사용자는 라벨만 변경하고 데이터는 그대로 둔다** → 마이그레이션 0. 기존 레코드의 일(day) 정보는 유지, 신규 입력만 `01` 고정

#### 공수 외 부가 이득

- 미국 부모는 앱에 아이 실명을 넣는 데 저항이 크다 → "Nickname"이 온보딩 이탈률에 유리
- 챗봇의 정서적 가치 손실 없음 — 애칭이 오히려 자연스럽다

- [ ] **미션 데이터의 문화 의존도가 미측정** — 480건 중 몇 %가 한국 특수 맥락인지 아직 모름. §5.5 공수의 최대 변수 → **선행 샘플 검수(50건) 0.5MD로 비율부터 재기**
- [ ] 로케일 혼재 시 `MissionFeedbackKeyword`·`WeeklyReportKeyword` 집계가 언어별로 쪼개짐 → 통계 화면 영향
- [ ] 기존 KR 사용자에게 회귀 없어야 함 — locale 기본값 `ko` 유지, en 미번역 시 ko fallback
- [ ] 이용약관·개인정보처리방침이 현재 **Notion 외부 링크 리다이렉트** (`app/policy/*/page.tsx`) → 영문 페이지도 Notion에 별도 생성·언어별 분기 필요
